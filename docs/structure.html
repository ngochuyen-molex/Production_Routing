ROUTING - Project Structure

One installable package, routing (pip install -e .), with three jobs: pre-checks against SAP data in Snowflake, OpCenter upload files, and the SAP routing automation that replaces UiPath (routing run).

This page shows the shape of the code (as built, 2026-11-19). The design, the reasons and the status are in architecture.md; what is checked or still open is only in verification.md; how to run is in README.md.

How the layers depend on each other

Imports only go downward. sap/ never imports Snowflake code and resolve/ never touches SAP, so each can be tested alone. One check never imports another check.

What goes in each folder

foundation

core/

Config (plant, connection), Snowflake / SQL Server connections, cleaning, Excel I/O. Written once.

queries

data/

Only SQL, bound parameters, batched material lists. One module per SAP domain; similar queries in one module are intentional.

business logic

checks/ & opc/

Stand-alone checks (check_xxx(df) + run(path)) and OpCenter upload files. Still usable on their own.

business logic

model/

Three kinds kept apart: Request (what the user asks), Entity (what exists in SAP), Result (what happened). The routing-matching rule lives once, on the entities.

business logic

resolve/ & layouts/

resolve/ turns Snowflake rows into entities. layouts/ holds each department's operation layout as data, not one script per department.

SAP

sap/

SAP GUI scripting: session, element ids, tables, one module per screen group. No business rules. Errors leave SAP without saving.

SAP

steps/

One class per action: plan() decides from Snowflake (Plan sheet), run() does it in SAP and returns a StepResult.

orchestration

pipelines/

run plans every row, runs the phases, writes RESULT_ columns and saves after each row. pre_uipath chains two checks for UiPath.

entry point

cli.py

One routing command; file path as argument (or asked), so it runs unattended.

Rules

  1. One job per layer: SQL in data/, rules in model/ / checks/ / layouts/, SAP screens in sap/, files and arguments in pipelines/ / cli.py.
  2. Element ids in one place: sap/elements.py; every new one is also logged in docs/uipath/ui_elements.md.
  3. No hardcoded values: plant and connection in core/config.py, credentials in .env, file paths as arguments.
  4. Safe SQL: bound parameters, never string-built material lists.
  5. Safe SAP: Save is only the last action of a step; any failure leaves SAP without saving.
  6. Verify by comparison: a changed check must give the same output as before on the same input.
